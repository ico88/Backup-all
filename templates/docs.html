Come funziona

Il sistema lavora con tre blocchi fondamentali che si collegano tra loro:

Ordine consigliato: configura prima le sorgenti, poi le destinazioni, infine crea i job che le collegano.
Requisiti di sistema
Server Linux (sorgente)
  • Accesso SSH (porta 22 di default)
  • Utente con permessi sudo (per dump DB)
  • mysqldump o pg_dump installati se usi DB
  • sshpass sul server Backup-All (non sulla sorgente)
Server Windows (sorgente)
  • WinRM abilitato (porta 5985)
  • Utente Administrator (o con delega WinRM)
  • Share SMB sul QNAP configurata (per wbadmin)
  • WinRM: winrm quickconfig + Set-Item WSMan:\localhost\Client\TrustedHosts *
VMware ESXi (sorgente/replica)
  • ESXi raggiungibile su porta 443
  • Utente con permesso datastore + VM power
  • ovftool installato su Backup-All (per replica)
  • Modalità manutenzione NON attiva sulla VM
Destinazione QNAP / NAS
  • SSH abilitato (metodo rsync — consigliato)
  • Cartella di destinazione creata e con permessi scrittura
  • Spazio sufficiente per il numero di copie configurate
Rete
  • Backup-All deve raggiungere le sorgenti e le destinazioni
  • Le sorgenti non devono raggiungere Backup-All
  • Firewall: apri le porte SSH/WinRM verso Backup-All
1 Configurare le sorgenti Vai alle sorgenti
Linux
  1. Seleziona il tab Linux
  2. Inserisci IP, porta SSH (default 22), utente e password
  3. Se vuoi fare backup di un'applicazione, compila la sezione Dati applicazione: nome app, tipo DB, percorsi dei dati
  4. Clicca Testa connessione — verifca SSH prima di salvare
  5. Clicca Salva sorgente Linux
Se usi autenticazione con chiave SSH invece che password, lascia la password vuota e assicurati che la chiave pubblica del server Backup-All sia in ~/.ssh/authorized_keys sulla sorgente.
Windows
  1. Seleziona il tab Windows
  2. Inserisci IP, porta WinRM (default 5985), utente Administrator e password
  3. Per il backup bare-metal tramite wbadmin, configura una share SMB nella destinazione (campo "Share SMB")
  4. Clicca Testa connessione — verifica che la porta WinRM risponda
  5. Clicca Salva sorgente Windows
Per abilitare WinRM su Windows Server: apri PowerShell come amministratore ed esegui winrm quickconfig -y. Se il firewall blocca la porta 5985, aggiungi la regola: netsh advfirewall firewall add rule name="WinRM" protocol=TCP dir=in localport=5985 action=allow
VMware
  1. Prima di tutto, aggiungi un host ESXi dalla sezione in fondo al tab VMware: inserisci IP host, porta (443), utente e password ESXi
  2. Seleziona l'host ESXi dal menu a tendina — la lista delle VM si carica automaticamente
  3. Seleziona la VM da proteggere
  4. Clicca Testa connessione ESXi — verifica accesso pyvmomi all'host
  5. Clicca Salva sorgente VMware
Il backup VMware produce un file OVF/OVA sul NAS. La VM viene messa in snapshot temporaneamente durante l'esportazione. La VM rimane accesa durante il processo (il backup è consistente a livello applicativo, non a caldo).
2 Configurare le destinazioni Vai alle destinazioni

Una destinazione è il NAS/QNAP dove vengono salvati i backup. Puoi avere più destinazioni e assegnare job diversi a ciascuna.

rsync over SSH Consigliato
  • Trasferisce solo le differenze (incrementale)
  • Crittografato (SSH)
  • Funziona con qualsiasi NAS con SSH abilitato
  • Porta di default: 22
API QTS
  • Usa le API native QNAP QTS
  • Porta di default: 8080
  • Richiede QNAP con QTS 5.x
  • Utile se SSH è disabilitato sul QNAP
  1. Inserisci il nome e l'IP del NAS
  2. Scegli il metodo (rsync SSH consigliato)
  3. Inserisci utente e password del NAS
  4. Indica il percorso base dove salvare i backup (es. /share/Backup). La cartella deve esistere sul NAS.
  5. Se hai Windows con wbadmin, compila anche la share SMB (es. Backup)
  6. Clicca Testa connessione per verificare subito
  7. Clicca Salva destinazione
QNAP — abilitare SSH: Nel pannello di controllo QTS → Applicazioni → SSH → attiva il servizio. Per sicurezza, usa una porta non standard (es. 2222) e disabilita il login root se possibile.
3 Creare un job di backup Vai ai job

Un job collega una sorgente a una destinazione e definisce quando e come eseguire il backup.

Backup Completo
Linux: tutti i dati app + dump DB + snapshot VM (se VMware configurato).
Windows: wbadmin bare-metal + dati applicativi.
Solo Dati Applicativi
Copia i percorsi configurati nella sorgente + dump del database. Più veloce del completo.
Snapshot OVF (VMware)
Esporta la VM completa come file OVF sul NAS. Solo per sorgenti VMware.
Pianificazione (cron)
PresetEspressione cronDescrizione
Ogni notte0 2 * * *Alle 02:00, tutti i giorni
Settimanale0 3 * * 0Domenica alle 03:00
Solo feriali0 1 * * 1-5Lun–Ven alle 01:00
Ogni 6 ore0 */6 * * *Alle 00:00, 06:00, 12:00, 18:00
Retention

Il campo Copie da mantenere indica quanti backup conservare. Quando viene superato il limite, il backup più vecchio viene eliminato automaticamente. Es.: con 7 copie e backup notturno, mantieni sempre l'ultima settimana.

4 Replica VM (warm standby) Vai alla replica

La replica VM crea e mantiene una copia "standby" di una VM VMware su un host ESXi (lo stesso o uno diverso). In caso di guasto, la VM standby viene avviata e prende il posto della primaria.

Come funziona la sincronizzazione
  • Lo strumento ovftool copia la VM primaria sull'host di destinazione
  • La VM standby viene sovrascritta ad ogni sync (flag --overwrite)
  • La VM standby rimane spenta finché non avviene un failover
  • La sincronizzazione segue un orario cron configurabile
Auto-failover (opzionale)
  • Il sistema controlla ogni 60 secondi se la VM primaria è accesa (pyvmomi)
  • Opzionalmente verifica anche la risposta di rete sull'IP configurato
  • Dopo N fallimenti consecutivi (configurabile), avvia automaticamente la standby
  • Il job viene messo in pausa dopo il failover per evitare sovrascritture
Procedura di configurazione
  1. Assicurati di avere almeno due host ESXi configurati (o uno se la standby è sullo stesso host)
  2. Vai su Replica VM e clicca + Nuova replica
  3. Seleziona l'host e la VM sorgente (la primaria)
  4. Seleziona l'host destinazione e inserisci il nome che avrà la VM standby
  5. Configura la pianificazione cron (es. ogni ora: 0 * * * *)
  6. Se vuoi l'auto-failover, attiva il toggle e configura intervallo e soglia di fallimenti
  7. Clicca Salva — la prima sincronizzazione partirà al prossimo ciclo cron. Per avviarla subito, usa il pulsante Sync ora
Requisito: ovftool di VMware deve essere installato sul server Backup-All. Se non è presente, apparirà un avviso nella pagina Replica VM. Scarica ovftool dal sito VMware Developer e installalo con il bundle .bundle fornito.
Failover manuale: prima di promuovere la VM standby, assicurati che la VM primaria sia effettivamente spenta o isolata. Avviare entrambe in contemporanea (split-brain) può causare conflitti di rete o corruzione dei dati.
Impostazioni Vai alle impostazioni
Generali
  • Nome organizzazione — appare nella topbar e nelle email di notifica
  • Cambio password — accessibile dal menu utente in alto a destra
Notifiche Email (SMTP)
  • Inserisci host SMTP, porta, utente e password
  • Attiva TLS se richiesto dal provider
  • Usa il pulsante Test SMTP per verificare la configurazione
  • Ogni job può avere un'email destinataria diversa
Domande frequenti

Il test verifica solo la connettività di base (SSH/WinRM/VMware API). Il backup può fallire per motivi diversi: permessi insufficienti sulla directory di destinazione, mysqldump non installato, disco pieno, timeout durante la copia. Controlla i log del job nella sezione Storico per il messaggio di errore preciso.

Vai su Job di Backup, trova il job e clicca il pulsante Esegui ora (icona play). Il backup parte immediatamente in background. Puoi seguire l'avanzamento nella sezione Storico.

Il ripristino è manuale. I backup vengono salvati nel percorso base della destinazione, organizzati in sottocartelle per nome job e data. Per Linux/dati app: copia i file via rsync o SCP. Per Windows wbadmin: utilizza wbadmin start recovery o il tool grafico "Ripristino di sistema". Per VMware OVF: importa il file OVF dall'interfaccia ESXi o con ovftool.

Lo scheduler APScheduler non avvia lo stesso job se è già in esecuzione (misfire policy). Il job successivo partirà normalmente al ciclo pianificato successivo.

Potrebbe essere che ovftool sia ancora in esecuzione o sia crashato. Verifica su Linux con ps aux | grep ovftool. Se il processo non esiste più, il job è rimasto "bloccato" per un crash inatteso. Riavvia il servizio Backup-All — al riavvio i job in stato RUNNING vengono automaticamente chiusi. Poi lancia una nuova sync manuale.

Usa lo script update.sh nella directory di installazione (/opt/backup-all/update.sh). Esegui sudo bash update.sh. Lo script scarica l'ultima versione dal branch configurato, aggiorna le dipendenze Python e riavvia il servizio. Il database e la configurazione vengono preservati.
